# Service worker 唤醒延迟：实测记录（结论：不改机制）

> 这份文档是 P7 的收尾记录。结论一句话：**在正常使用下，native 与 WebSocket 两种传输都没有可测出的冷启动停顿，
> 因此不引入任何"保活"机制。**

## 背景

扩展的 service worker（SW）会被浏览器在空闲后回收。理论上的最坏情况是：命令到达时 SW 正被回收，
只能等 `chrome.alarms` 的兜底重连（周期 `0.5` 分钟 = **30 秒**）把它叫醒，于是调用方白等。

相关实现（`extension/background.js`）：

- `chrome.alarms.create('page-bridge-reconnect', { periodInMinutes: 0.5 })` + 对应监听 → 每 30 秒兜底重连；
- `chrome.tabs.onActivated` / `chrome.tabs.onUpdated` → 切/加载标签页本来就会唤醒；
- `scheduleReconnect()` 带退避，`connect()` 是唯一连接入口。

⚠️ 口径说明：**生产安装的扩展不能依赖低于 30 秒的 alarm 周期**；Chrome 文档说明
**未打包扩展在调试时不受该频率限制**（<https://developer.chrome.com/docs/extensions/reference/api/alarms>）。
所以"30 秒"是生产环境的现实下限，而不是绝对下限。这个维度上不存在可优化的空间 —— 不要试图把轮询改快。

## 测量方法与结果

测量方式：**冷却后的第一条命令** 与 **紧随其后的热态中位数** 之差。两者都包含 node 启动等固定开销，
相减即可抵消，剩下的差值就是唤醒相关的成本。

| 传输方式 | 冷却后第一条 | 热态中位数（4 条） | 增量 |
|---|---|---|---|
| native | 168 ms | 146 ms | **+22 ms** |
| WebSocket（仅 WS 模式） | 163 ms | 173 ms | **−9 ms** |

两次测量都在冷却数分钟（>3 分钟）之后进行，期间不触碰扩展；测量时 `/status` 的 `via` 分别为 `native` 与 `ws`，
确认测的就是对应传输。

## 解释

两个增量都落在 ±20 ms 的噪声范围内，即**测不出冷启动停顿**。原因是两条传输各自持有一条长连接：

- native 模式：bridge 与扩展之间常驻一个 native port；
- WS 模式：扩展主动连 `ws://127.0.0.1:8799/ws`，连接本身常驻。

长连接会持续重置 SW 的空闲计时，SW 因此在正常使用中基本不会被回收 —— "等到 30 秒闹钟"的路径实际很难走到。

## 已知未测（诚实标注）

**没有**人为强制一次真正的 SW 驱逐（例如让浏览器空闲数小时、或撞上 Chrome 对 SW 的硬性上限），
因此"真的被回收后第一条命令要等多久"这个极端场景**仍未测得**。当时的替代口径（冷热之差）覆盖的是常规使用。

若日后真的遇到这个极端场景，需要的测量口径是：bridge 在命令里带上**发送时间戳**，扩展处理时回报收到时间，
两端相减 —— 只有这样才测得到"从被驱逐到开始处理"的那一段；当前 bridge 不打时间戳，端到端计时测不到它。

## 结论与后续

1. **不引入保活机制**：没有证据表明存在问题；为保活注入常驻页面 UI 会与站点样式打架，
   用无意义定时器硬撑 SW 存活则会被 Chrome 惩罚且耗电。
2. 若将来出现真实投诉（例如长时间空闲后第一条命令明显变慢），按上面的"发送时间戳"口径补测，再决定手段。
3. 相关实现与测试：`extension/background.js`（`connect()` / `scheduleReconnect()` / alarms）、
   `dev/sw-load-test.mjs`（假 `chrome` API 下的重连调度断言）。
